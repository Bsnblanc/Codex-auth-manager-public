# 并发开发边界说明

## 记录目的

这份文档记录的是：

- 当一个需求正在开发时
- 又来了一个和它不相干的新需求
- 应该如何判断能不能并发推进
- 如果能并发，应该怎样实际操作才不互相踩改动

这份文档不是讲“一个需求内部怎么拆子任务”。

它讲的是：**两个不同需求如何同时推进。**

## 1. 先明确这里说的“并发”是什么

这里的并发，不是指：

- 在同一个工作目录里同时改两套需求
- 一边改刷新逻辑，一边顺手把别的需求也塞进去
- 不建隔离分支，直接把多个需求堆在一起开发

这里说的并发，指的是：

- 每个需求各自有独立分支
- 最好各自有独立 worktree
- 每个需求只改自己的边界
- 最后再按稳定程度分别合并

一句话：

> 并发开发的前提不是“同时写代码”，而是“先把冲突边界隔离开”。

## 2. 最核心的判断标准

判断两个需求能不能并发，先问这四个问题。

### 2.1 问题一：A 的结果会不会决定 B 怎么做

如果会，不能并发。

例如：

- 需求 A 在改刷新策略
- 需求 B 在改自动切号逻辑

因为 B 的实现方式会受 A 影响，所以不能真正并发落地。

### 2.2 问题二：两个需求会不会改同一个热点文件

如果会，高风险，默认不要并发直接改。

原因不是“同一个文件永远不能一起改”，而是：

- 热点文件通常承载多条主链路
- 同一个文件里的两处改动常常会互相影响
- 最终冲突不只是 git 冲突，更是语义冲突

### 2.3 问题三：两个需求会不会改同一个状态契约或 IPC 语义

如果会，默认串行。

例如：

- 都要改 `DashboardState`
- 都要改 `ManagedAccount.lastQuota` 的含义
- 都要改 `accounts:activate` 的行为

这些即使落在不同文件，也不是独立任务。

### 2.4 问题四：一个需求的结论会不会让另一个需求返工

如果大概率会返工，也不要并发实现。

表面上看是两条任务，实际上只是把返工时间提前了。

## 3. 这个仓库里的高冲突区

以下文件在当前项目里属于高冲突区。

### 3.1 Renderer 热点

- `src/App.tsx`
- `src/styles.css`

原因：

- `src/App.tsx` 集中了状态加载、自动刷新调度、hover/focus、图表、工具栏动作
- `src/styles.css` 集中了交互视觉和许多容易互相覆盖的样式规则

### 3.2 Main-process 热点

- `electron/main.cts`
- `electron/auto-switch.ts`
- `electron/store.ts`
- `electron/types.ts`

原因：

- `electron/main.cts` 串起了 IPC、刷新、导入导出、激活、持久化
- `electron/auto-switch.ts` 会影响切号决策
- `electron/store.ts` 和 `electron/types.ts` 会影响整个应用的状态契约

### 3.3 文档热点

- `docs/product-spec.md`
- `AGENTS.md`

原因：

- 这些文件描述的是全局规则和产品语义
- 一旦改动，会影响后续所有实现决策

## 4. 什么样的新需求可以并发推进

以下情况通常可以并发：

- 只改 `docs/` 中与当前主链路无关的说明
- 只改某个独立导入/导出细节，不碰刷新/切号链路
- 只改构建脚本、打包配置、非共享状态的工具代码
- 只改独立 UI 区块，且不碰 `src/App.tsx` 同一热点区域
- 只改和 quota/refresh 无关的新 IPC

它们可以并发的前提是：

- 不改同一状态结构
- 不改同一 IPC 行为
- 不改同一条核心流程

## 5. 什么样的新需求不要并发直接实现

以下情况默认不要并发实现：

- 都会改 `src/App.tsx` 的刷新 effect 或工具栏行为
- 都会改 `electron/main.cts` 的 refresh / activate / import 主流程
- 都会改 `ManagedAccount`、`DashboardState`、`history`、`lastQuota` 的语义
- 一个需求在改产品语义，另一个需求已经基于旧语义开始写实现
- 一个需求的结果会改变另一个需求的接口、字段或流程顺序

这些情况应该先收敛主需求，再让新需求基于稳定边界继续。

## 6. 标准做法：不要在同一个工作目录里并发做两个需求

正确做法是：

1. 一个需求一个分支
2. 最好一个需求一个 worktree
3. 每个 worktree 只做一个稳定目标

原因：

- 同一个目录里混多个需求，git diff 会很快失去边界
- 你很难在中途安全切换上下文
- 修一个需求时容易顺手污染另一个需求
- 最后代码 review、测试、回滚、提交都会变困难

## 7. 推荐操作流程

下面是一套最稳的实际操作方式。

### 第一步：先确认当前正在做的需求占用了哪些热点文件

例如当前正在改“刷新策略”，那它大概率占用：

- `src/App.tsx`
- `electron/main.cts`
- `electron/auto-switch.ts`
- `docs/product-spec.md`

这一步的目的，是先划出“禁区”。

### 第二步：判断新需求是否碰这些禁区

如果新需求：

- 不碰这些文件
- 不碰这些状态语义
- 不碰这些 IPC 行为

就可以进入并发轨道。

如果会碰，就不要并发直接改。

### 第三步：为新需求创建独立分支

示例：

```bash
git switch main
git pull
git switch -c feature/export-improvements
```

原因：

- 新需求必须有自己的历史边界
- 后续即使刷新需求还没完成，也不影响这个新需求单独提交或合并

### 第四步：最好为新需求创建独立 worktree

示例：

```bash
git worktree add "..\band-export-improvements" -b feature/export-improvements main
```

原因：

- 你不需要反复 stash / checkout
- 两个需求的未提交改动天然隔离
- 你可以同时打开两个目录分别开发和验证

### 第五步：在新 worktree 里只做该需求自己的实现

原则：

- 不顺手修当前主需求的东西
- 不顺手整理别的热点文件
- 不把“顺便的小改动”混进来

原因：

- 一旦混入跨需求改动，两个分支就重新耦合了

### 第六步：各自独立验证

每个需求都在自己的 worktree 中单独做验证，例如：

- `npm run lint`
- `npm run build`
- 对应需求的手动检查

原因：

- 验证结果必须绑定到该分支的实际改动
- 不能拿另一个需求分支上的验证结果来证明这里没问题

### 第七步：谁先稳定，谁先合并

顺序可以是：

1. 新需求先稳定 -> 先合
2. 主需求后稳定 -> 再 rebase / merge 最新主线
3. 解决冲突后再做最终验证

原因：

- 并发开发的目标不是“完全不冲突”
- 而是把冲突控制在最后一次、可判断、可验证的收口阶段

## 8. 为什么 worktree 比频繁 stash 更适合这个场景

`stash` 适合短暂切换。

但当两个需求都要持续推进时，`stash` 会带来几个问题：

- 容易忘记 stash 里放的是什么
- 容易把不完整改动反复弹来弹去
- 发生冲突时更难判断是谁的问题

而 `worktree` 的好处是：

- 每个需求始终在自己的目录里
- 每个目录都有自己的未提交状态
- 不需要来回藏改动

所以对于“一个需求还没做完，另一个全新需求又来了”的场景，优先用 `worktree`。

## 9. 一个最常见的错误

最常见的错误不是“不会并发”，而是：

> 以为两个需求逻辑不一样，所以可以直接一起改。

实际上，两个需求即使业务目标不同，只要共享下面任意一项，就不是真独立：

- 同一个状态结构
- 同一个 IPC
- 同一个调度链路
- 同一个热点文件
- 同一个产品语义

这时正确做法不是硬并发，而是先收敛边界。

## 10. 在当前项目里的具体应用示例

假设当前需求是“改刷新策略为 active live、inactive last-known、切号时校验”。

### 10.1 不适合并发直接做的需求

- 改自动切号规则
- 改 `accounts:activate` 语义
- 改 quota 数据结构
- 改聚合图表如何解释 inactive 数据

原因：

- 这些都共享刷新策略的状态边界或行为语义

### 10.2 适合并发推进的需求

- 新增导出文件命名规则
- 增加某个独立文档
- 优化与刷新无关的菜单交互
- 打包或构建脚本调整

原因：

- 它们不决定刷新策略怎么实现
- 它们也不依赖刷新策略的最终字段含义

## 11. 最后的执行原则

记住三句话就够了：

1. **不同需求先分支隔离。**
2. **长期并发优先 worktree，不要长期依赖 stash。**
3. **只要共享热点文件、状态契约或产品语义，就默认串行。**

一句话总结：

> 不相干需求要并发，靠的不是“同时改”，而是“先隔离，再各自稳定，最后统一收口”。
