# 全新项目从零开始开发流程说明（以 OpenCode Codex Auth Manager 为例）

## 记录目的

这份文档不是记录某一个 bug，也不是记录某一轮改动。

它要解决的问题是：当面对一个“全新项目”时，应该按什么顺序推进，为什么这个顺序不能跳步，以及哪些环节可以并发、哪些环节必须串行。

本文档使用当前项目作为完整示例：

- 项目名称：OpenCode Codex Auth Manager
- 项目目标：做一个 Windows 桌面程序，统一管理 OpenCode 使用的 Codex/OpenAI 账号，并查看和切换账号额度状态

## 0. 先明确这份流程适用于什么场景

这份流程适用于：

- 从零创建一个新项目
- 目录和代码都还没有稳定结构
- 需求、边界、第一版范围还需要逐步收敛

这份流程不适用于：

- 接手一个已有成熟代码库
- 已有完整产品方案，只差执行实现
- 纯修一个已知小 bug

## 1. 第一步：定义目标

### 1.1 这一步在做什么

目标的意思是：这个项目到底要解决什么问题。

目标不是功能列表，而是一句能说明项目价值的话。

### 1.2 为什么必须先做

如果连项目要解决的问题都说不清，就不应该进入技术选型、界面设计或代码实现。

因为：

- 功能是手段，不是方向
- 技术是实现方式，不是目标本身
- UI 只是表现层，不是项目存在的原因

### 1.3 本项目示例

当前项目的一句目标可以写成：

> 做一个 Windows 桌面应用，集中管理 OpenCode 使用的 Codex/OpenAI 账号，并让用户在一个界面里查看额度和切换当前使用账号。

### 1.4 输出结果

这一步必须产出一句清晰目标。

如果一句话说不清，停止往后走。

## 2. 第二步：定义使用场景

### 2.1 这一步在做什么

使用场景的意思是：谁会怎么使用它，以及希望得到什么结果。

这里不能写抽象口号，必须写成顺序动作。

### 2.2 为什么必须在前面做

如果不知道用户到底怎么操作，后面的功能清单就很容易是拍脑袋列出来的。

### 2.3 本项目示例

可以写成这样：

1. 用户打开应用。
2. 用户导入一个 Codex/OpenAI 账号。
3. 应用读取该账号的授权信息并查询额度。
4. 用户再导入第二个账号。
5. 应用在同一界面显示所有账号的额度状态。
6. 用户点击某个账号，把它切换成 OpenCode 当前使用的账号。
7. 用户继续查看所有账号的剩余额度和历史变化。

### 2.4 输出结果

这一步必须产出用户操作路径。

如果只能说“做一个方便管理账号的平台”，说明还没进入可开发状态。

## 3. 第三步：定义边界

### 3.1 这一步在做什么

边界的意思是：这次明确不做什么。

### 3.2 为什么必须先做

不先定义边界，项目会在第一轮就不断扩张，最后谁都不知道第一版该在哪停。

### 3.3 本项目示例

第一版的明确边界可以是：

- 不做网页版本
- 不做多页导航
- 不做非 Codex/OpenAI 提供方管理
- 不做团队协作功能
- 不做复杂报表后台

### 3.4 输出结果

这一步必须列出排除项。

如果“以后想做的功能”仍然不断混进第一版，说明边界还没收敛。

## 4. 第四步：定义验收标准

### 4.1 这一步在做什么

验收标准的意思是：什么结果算第一版完成。

### 4.2 为什么这一步不能省

如果不能检查“是否完成”，就无法判断该继续扩功能还是该先收口。

### 4.3 本项目示例

第一版验收标准可以是：

- 用户至少能导入两个账号
- 页面能显示每个账号的当前额度
- 用户能切换当前使用账号
- 切换时不会覆盖无关 provider 配置
- 项目可以成功构建并启动

### 4.4 输出结果

这一步必须得到一组可检查的结果，而不是“界面差不多了”“应该能用了”。

## 5. 第五步：定义第一版范围

### 5.1 这一步在做什么

第一版范围的意思是：在目标、场景、边界、验收标准已经明确后，这一轮到底先做哪些最小功能。

### 5.2 为什么放在这里

只有前面四步都清楚，才能真正筛出“最小可用版本”应该包含什么。

### 5.3 本项目示例

第一版范围可以收敛为：

- 导入账号
- 保存账号
- 拉取并显示额度
- 切换当前账号
- 显示简单历史趋势

暂时不做：

- 高级筛选
- 权限管理
- Web 版同步
- 多人协作

### 5.4 输出结果

这一步必须得到一份最小功能清单。

## 6. 第六步：技术选型

### 6.1 这一步在做什么

技术选型的意思是：根据第一版范围，决定运行平台、语言、框架、存储方式。

### 6.2 为什么技术选型不能提前

如果一开始就先选技术，很容易出现“为了迁就技术而扭曲需求”的问题。

### 6.3 本项目示例

基于当前目标和环境，实际选型可以是：

- Windows 桌面应用
- Electron 作为桌面容器
- React 作为界面层
- TypeScript 作为主语言
- 本地 JSON 作为 MVP 存储方式

### 6.4 输出结果

这一步必须明确平台、框架、语言、存储方案。

## 7. 第七步：建立最小工程骨架

### 7.1 这一步在做什么

工程骨架的意思是：先把项目搭成一个能启动、能构建、能检查的最小工程。

### 7.2 为什么这一步先于业务代码

如果工程本身都不能稳定运行，后面越写业务代码，排查成本越高。

### 7.3 本项目示例

本项目的骨架包括：

- `package.json`
- Electron 主进程入口
- Renderer 入口
- Vite 配置
- 基本命令：`dev`、`lint`、`build`

### 7.4 输出结果

这一步至少要做到：

- 项目能启动
- 项目能构建
- 项目能做基础检查

## 8. 第八步：做结构分析并沉淀规则

### 8.1 这一步在做什么

当项目骨架出来后，要对目录结构、热点文件、主要职责、反模式做一次结构分析，并写成 `AGENTS.md`。

### 8.2 为什么不是一开始就做

因为在骨架出来之前，目录还是空的，结构分析没有真实对象可写。

### 8.3 本项目示例

这个项目完成结构分析后，得到的核心域就是：

- `electron/`：主进程、IPC、auth、quota、store
- `src/`：单页 UI、hover/focus、图表、样式
- `docs/`：产品规则、字段说明、任务记录

并最终生成了：

- `AGENTS.md`
- `electron/AGENTS.md`
- `src/AGENTS.md`

### 8.4 输出结果

这一步要得到：

- 项目结构规则
- 热点文件说明
- 反模式与验证要求

## 9. 第九步：定义数据结构

### 9.1 这一步在做什么

数据结构的意思是：系统要保存、传递、展示哪些数据，每种数据长什么样。

### 9.2 为什么数据必须先于 UI

UI 只是数据的表现层。数据结构不清，界面几乎一定会反复推倒重来。

### 9.3 本项目示例

本项目的数据结构包括：

- `ManagedAccount`
- `QuotaSnapshot`
- `QuotaWindowSnapshot`
- `DashboardState`
- `AppStore`

这些都定义在 `electron/types.ts` 一类文件里。

### 9.4 输出结果

这一步必须产出明确的数据模型。

## 10. 第十步：定义核心流程

### 10.1 这一步在做什么

核心流程的意思是：用户做一个动作后，系统内部怎样一步步完成。

### 10.2 为什么必须画成顺序链路

只有写成链路，才能看出哪些地方是前置依赖、哪些地方可以拆模块、哪些地方会形成热点。

### 10.3 本项目示例

导入账号这条核心流程可以写成：

1. 用户点击导入账号。
2. 主进程读取 auth 内容。
3. 解析 JWT 字段。
4. 查询 quota。
5. 写入本地 store。
6. 增加 history。
7. Renderer 读取最新 state。
8. 页面显示账号和额度。

### 10.4 输出结果

这一步必须得到一条或多条“输入 -> 处理 -> 存储/同步 -> 输出”的链路。

## 11. 第十一步：划分模块

### 11.1 这一步在做什么

模块的意思是：把不同职责拆到不同目录或文件域。

### 11.2 为什么模块划分要放在数据和流程之后

如果数据和流程都不清楚，模块划分就只能靠感觉，后面会反复重构。

### 11.3 本项目示例

基于数据和流程，这个项目的模块划分可以是：

- `electron/store.ts`：持久化
- `electron/jwt.ts`：JWT 解析
- `electron/quotas.ts`：额度拉取
- `electron/opencode.ts`：auth merge/sync
- `electron/main.cts`：IPC 和主流程串联
- `src/App.tsx`：主页面行为
- `src/styles.css`：样式层

### 11.4 输出结果

这一步必须得到清晰职责边界，而不是“都先写进一个文件再说”。

## 12. 第十二步：优先做第一条闭环

### 12.1 这一步在做什么

闭环的意思是：从用户一个操作开始，到用户真正看到结果结束的一整条链路。

### 12.2 为什么先做闭环

先证明“一条完整链路能跑通”，比先堆很多半成品功能更重要。

### 12.3 本项目示例

这个项目的第一条闭环可以是：

1. 导入一个账号
2. 写入 store
3. 页面显示这个账号

第二条闭环才是：

1. 导入账号
2. 成功拉取 quota
3. 页面显示额度状态

第三条闭环再是：

1. 点击账号
2. 切换 OpenCode 当前使用账号
3. 页面反映新的 active 状态

### 12.4 输出结果

每一条闭环都必须是用户真正可见的完整链路。

## 13. 第十三步：进入重复开发节奏

### 13.1 这一步在做什么

第一条闭环跑通后，后续每一轮都按固定节奏重复，不重新发明流程。

### 13.2 标准节奏

每一轮都按：

1. 读取上下文
2. discovery
3. 最小实现
4. 验证
5. 记录
6. checkpoint

其中第 5 步“记录”必须包含：

- 本轮用户提问和关键回复
- 主线如何理解本轮目标
- 本轮明确不做什么
- 实际方案、输出和结果
- 验证证据和未解决项

### 13.3 本项目示例

比如后续修“hover 零额度 marker 一起高亮”的问题时，也是同样的节奏：

1. 先看产品规则
2. 再查 `src/App.tsx` 和 `src/styles.css`
3. 做最小修复
4. 跑 `npm run lint` 和 `npm run build`
5. 补 `docs/quota-hover-marker-task-record.md`
6. 再提交保存节点

### 13.4 每一轮都要先指定记录者

从第一条闭环开始，后续每一轮都必须明确：

- 谁是这轮的记录者
- 记录要写到哪个文档

默认规则：

- 如果没有单独分出记录线，就由主线负责记录

记录者的职责不是最后补一句“已完成”，而是要把下面这些一起留痕：

- 用户原始要求
- 用户后续修正
- 本轮方案
- 实际输出
- 验证结果
- 下一步边界

如果这些内容还没落档，就不应该直接进入下一轮闭环。

## 14. 并发规则分析

不是所有阶段都适合并发。

真正的高效率，是把“调查并发”和“实现串行”区分清楚。

### 14.1 必须串行的环节

以下环节前后依赖很强，必须顺序推进：

1. 目标 -> 使用场景 -> 边界 -> 验收标准 -> 第一版范围
2. 数据结构 -> 核心流程 -> 模块划分
3. 第一条闭环的真正实现
4. 最终验收结论、记录收尾、checkpoint 提交

原因：

- 后一步依赖前一步的结论
- 其中任何一步变化，都会改变后一步的实现方式

### 14.2 可以并发的环节

以下环节适合并发：

- 结构分析：目录、入口文件、配置文件、文档、LSP codemap
- discovery：repo 搜索、文档检索、AST/LSP 查询、外部资料查证
- 技术选型比较：在目标和范围已经稳定后，可以比较多个候选技术
- 验证中的独立检查：lint、build、静态诊断、独立测试
- 不影响当前决策的只读文档整理

原因：

- 这些工作彼此不改同一实现链路
- 这些工作的结果通常只是补充信息，而不是直接互相覆盖

### 14.3 有条件并发的环节

以下情况只有在前提稳定后才允许并发：

- 多模块实现
- 多人同时推进多个子任务
- 前后端同时开发

前提必须满足：

- 接口已经稳定
- 数据结构已经稳定
- 职责边界已经稳定

如果这些前提不稳定，就必须串行。

### 14.4 并发判断原则

判断某两件事能不能并发，最简单的问题是：

> A 的结果会不会决定 B 怎么做？

如果答案是：

- 会 -> 不能并发
- 不会 -> 可以并发

### 14.5 实际开发中的并发方式示例：项目启动后的 discovery

当这个项目刚有最小骨架时，最适合并发的不是写代码，而是做只读调查。

实际可以并发做的事包括：

- 读取 `docs/product-spec.md`，确认产品目标和范围
- 读取 `package.json`，确认 `dev`、`lint`、`build` 命令
- 读取 `electron/` 目录，确认主进程有哪些职责
- 读取 `src/` 目录，确认 renderer 入口和页面热点
- 做 LSP 符号分析，找 `App`、`computeAggregateBars`、`runStoreMutation` 这类中心符号

这些可以并发的原因是：

- 它们都在补上下文
- 它们不会相互覆盖
- 任何一个结果都不会直接改写另一项调查的结论

这个阶段的正确做法是：

1. 并行读文档、目录、入口、符号。
2. 收敛出项目结构和热点。
3. 再决定后面从哪个模块开始实现。

### 14.6 实际开发中的并发方式示例：第一条闭环前后的串并行切换

以这个项目的第一条闭环“导入账号后页面能显示账号”为例。

在真正写代码前，可以并发：

- 读 `electron/types.ts` 看账号数据结构
- 读 `electron/store.ts` 看本地存储方式
- 读 `electron/main.cts` 看导入入口
- 读 `src/App.tsx` 看页面如何接收 state

但一旦进入真正实现，就不能继续随意并发写：

1. 先确定账号数据结构。
2. 再确定导入后如何写入 store。
3. 再确定 renderer 如何读取并展示。

这里必须串行的原因是：

- `src/App.tsx` 的展示依赖 `DashboardState`
- `DashboardState` 的内容依赖 `electron/store.ts`
- `store` 写入路径又依赖 `electron/main.cts` 的导入流程

也就是说：

- 调查可以并发
- 实现必须按依赖顺序串行

### 14.7 实际开发中的并发方式示例：本项目 hover marker bug

后续这个项目实际修“hover 时两个零额度 marker 一起高亮”的 bug 时，也体现了并发和串行的边界。

当时适合并发做的事包括：

- 读 `docs/product-spec.md`，确认 hover 和 focus 的正式行为边界
- 读 `docs/quota-hover-marker-task-record.md`，确认前面误修过什么
- 读 `src/App.tsx`，确认 JS 逻辑有没有正确添加 `is-active` / `is-dimmed`
- 读 `src/styles.css`，确认样式层是否有覆盖关系

这一阶段并发是高效的，因为：

- 文档在回答“应该怎样”
- `src/App.tsx` 在回答“逻辑怎么写的”
- `src/styles.css` 在回答“视觉为什么不对”

但真正修复时，就必须收敛成串行动作：

1. 先确认需求边界不是“隐藏其他额度条”。
2. 再确认 `src/App.tsx` 实际已经给非当前 marker 打了 `is-dimmed`。
3. 最后才定位到真正根因：`.state-region.is-end` 覆盖了 dim 透明度。
4. 再只改 `src/styles.css`。

这说明：

- 多源调查可以并发
- 根因判断必须收敛成一个结论
- 最终修复仍然要最小化地落在一个确定模块里

### 14.8 实际开发中的并发方式示例：跨模块功能开发

假设这个项目下一步要做“区分同一用户下不同 team/account 容器并在界面展示”。

这个需求看起来会跨多个模块：

- `docs/subscription-identity.md`
- `docs/obtainable-fields.md`
- `electron/jwt.ts`
- `electron/quotas.ts`
- `electron/main.cts`
- `src/App.tsx`

这时正确的并发方式不是“六个文件同时开始写”，而是先把调查并发、实现串行：

可以先并发调查：

- 文档里当前证据允许说到哪一步
- `jwt.ts` 当前已经解析了哪些字段
- `quotas.ts` 当前把哪些字段带进快照
- `main.cts` 当前导入和刷新逻辑怎样写入账号
- `src/App.tsx` 当前界面已经显示了哪些身份信息

然后必须先收敛出一个统一结论：

- 先决定“team/account 容器”的判断依据
- 再决定这些字段要不要进入 store
- 再决定 UI 怎么显示

所以实现顺序大概率会是：

1. 文档结论确认
2. `electron/types.ts` / `electron/jwt.ts` 数据定义和解析
3. `electron/quotas.ts` / `electron/main.cts` 写入和主流程
4. `src/App.tsx` 展示
5. `docs/` 补记录

这里如果直接并发改 `main.cts` 和 `src/App.tsx`，很容易发生：

- 后端字段名还没定，前端先写错
- 展示方式先定了，但数据结构后面又变了
- 同一个需求被多个模块各自按不同理解实现

### 14.9 实际开发中的并发方式示例：验证阶段

验证阶段也不是全部串行。

适合并发的验证包括：

- `npm run lint`
- `npm run build`
- 改动文件的静态诊断
- 独立的只读 git 状态检查

这些检查可以并发，因为它们彼此不会改同一实现链路。

但结果判定仍然必须统一收口：

1. 先看有没有类型错误。
2. 再看构建是否通过。
3. 再结合手动 QA 判断功能是不是达到了验收标准。

也就是说：

- 检查动作可以并发
- 是否“已经完成”的结论不能并发拆开给出

### 14.10 实际开发中的错误并发示例

以下看起来像能并发，实际是高风险做法：

- 需求边界还没确认，就同时改 `electron/main.cts` 和 `src/App.tsx`
- 还没确认根因，就同时尝试三种 bug 修法
- 数据结构还没稳定，就让前端和主进程同时落实现
- 还没看验证结果，就提前写“已经完成”的记录和 commit message

这些做法的共同问题是：

- 一项工作的结果会改变另一项工作的实现方式
- 表面并发，实际返工
- 最终会比先收敛再实现更慢

### 14.11 全局工作流并发规则

前面的例子大多是“局部并发”，也就是同一条功能链里的并发调查或局部实现。

但全新项目真正的大并发，不是同一时间改很多文件，而是：

1. 先串行冻结共同契约。
2. 再把项目拆成几条独立工作流。
3. 再让这些工作流并发推进。
4. 最后再统一集成和验收。

这里的共同契约，至少包括：

- 目标和第一版范围
- 验收标准
- 核心数据结构
- 跨层接口
- 关键规则边界

如果这些东西还在变化，就不能做全局并发。

### 14.12 本项目里的全局工作流拆分示例

如果这个项目在最初阶段就按“全局并发”推进，可以拆成四条工作流：

#### A 线：主进程能力线

负责：

- JWT 解析

#### B 线：渲染层界面线

- 顶部额度条
- hover / focus 交互
- 图表与消息展示

对应模块：

- `src/App.tsx`

#### C 线：规则与文档线

### 14.13 这四条工作流为什么能并发

只有在下面这些前提已经冻结时，它们才能并发：

- `ManagedAccount`、`QuotaSnapshot`、`DashboardState` 这些核心数据 shape 已经定了
- preload 到 renderer 的接口 shape 已经定了
- 只管理 Codex/OpenAI auth 片段的规则已经定了
- `accountId`、`sameSubscription()`、身份边界这些规则已经定了

也就是说，本项目里至少要先稳定这些位置：

- `electron/types.ts`
- `electron/preload.cts`
- `src/global.d.ts`
- `docs/product-spec.md`
- `docs/subscription-identity.md`
- `docs/obtainable-fields.md`

一旦这些契约冻结：

- A 线不必等 B 线写完 UI 才能做 quota/store
- B 线不必等 A 线所有细节完成，先按稳定 state shape 搭页面
- C 线可以同步把已冻结规则写进文档
- D 线可以独立完善 build/lint/AGENTS/checkpoint 基线

### 14.14 本项目全局并发的具体实施步骤

如果把当前项目当成真正的全新项目，具体实施顺序可以这样写：

#### 第 1 阶段：串行收敛方向

1. 写目标：做一个 Windows 桌面应用，统一管理 OpenCode 使用的 Codex/OpenAI 账号。
2. 写场景：导入账号、显示额度、切换当前账号。
3. 写边界：不做 Web 版、不做非 Codex provider 管理、不做复杂后台。
4. 写验收标准：至少支持两个账号、显示额度、切换 active、可构建。
5. 收敛 MVP：导入、保存、额度展示、切换、简单历史。

这五步必须串行，因为后一步依赖前一步。

#### 第 2 阶段：串行冻结共同契约

1. 定义核心数据：`ManagedAccount`、`QuotaSnapshot`、`DashboardState`。
2. 定义接口契约：preload 暴露哪些方法、renderer 收到什么结果。
3. 定义规则边界：只管 Codex/OpenAI auth 片段，保留其他 provider，不夸大身份字段含义。

在当前项目里，对应的冻结点就是：

- `electron/types.ts`
- `electron/preload.cts`
- `src/global.d.ts`
- `docs/product-spec.md`
- `docs/subscription-identity.md`
- `docs/obtainable-fields.md`

#### 第 3 阶段：拆工作流并并发推进

冻结共同契约后，再并发推进四条线：

1. A 线写主进程导入、quota、store、auth sync。
2. B 线写页面骨架、账号列表、额度条、交互态。
3. C 线写产品规则、字段说明、结构和任务记录。
4. D 线完善 dev/build/lint、AGENTS、git/checkpoint 基线。

这里的关键约束是：

- 每条线只能改自己负责的模块
- 不允许擅自改共享契约
- 如果共享契约必须变化，先暂停并发，重新统一收敛

#### 第 4 阶段：串行集成

并发实现完成后，要回到一条主链统一接线：

1. 把主进程能力接到 preload。
2. 把 preload 接到 renderer。
3. 把真实 state 接到 UI 展示。
4. 把 import / refresh / activate 流程串成完整链路。

这一步必须串行，因为它在做真正的系统集成。

#### 第 5 阶段：并行验证

集成后可以并行跑独立检查：

- `npm run lint`
- `npm run build`
- 改动文件静态诊断
- git 状态检查

这些检查动作可以并发，但“是否已经完成”必须统一收口。

#### 第 6 阶段：串行收尾

1. 根据验收标准统一判断是否完成。
2. 补文档记录：问题、原因、改动、验证、未解决项。
3. 创建 checkpoint / commit。

这一步不能并发，因为它要输出一份唯一一致的项目结论。

### 14.15 哪些情况说明必须停止全局并发

如果出现下面任一情况，就说明不能继续并发推进：

- `src/App.tsx` 想用的数据字段还没在 `electron/types.ts` 定下来
- preload 接口还没定，renderer 已经先写死调用方式
- 主进程在改返回结构，UI 同时按旧结构继续开发
- 文档里对身份字段的解释还没定，业务代码已经按不同理解落地

这时正确做法不是继续并发，而是：

1. 暂停相关工作流
2. 回到共享契约收敛
3. 重新统一后再继续并发

### 14.16 结合 OMO 的真实工作方式，这套规则该怎样执行

上面的“全局工作流并发”是项目管理模型。

但当前 OMO 不是一个拥有多个独立工作树、多个长期并行编码分支的系统。

当前 OMO 更接近：

- 一个主代理负责收敛需求、冻结契约、维护 todo、决定停止条件、做最终集成和收口
- 多个子代理负责并行 discovery、并行只读分析、并行文档沉淀、以及少量边界清晰的独立实现子任务
- 所有结果最终仍然回到同一个工作区、同一条验证链、同一条 commit 收口线

所以，结合 OMO 的真实执行方式后，最正确的理解不是“所有工作流都长期并行写代码”，而是：

1. 主代理串行控共享契约。
2. 子代理并行产出独立结果。
3. 主代理统一集成和验证。

### 14.17 结合 OMO，真正可执行的并发形式有哪些

在当前系统下，最适合真正并发的内容是：

#### 第一类：并发 discovery

- explore 并行搜代码结构和模式
- librarian 并行查外部文档或参考实现
- 主会话同时读取关键文件、文档、LSP 信息

这是最稳定、收益最高的并发。

#### 第二类：并发文档与规则沉淀

当主线已经确认结论后，可以并发做：

- 产品规则整理
- 字段说明整理
- 任务记录整理
- AGENTS.md 结构沉淀

这类工作通常不改共享实现链路，所以很适合并发。

#### 第三类：并发独立实现子任务

只有在共享契约已经冻结时，才适合做这类并发：

- 一个子任务负责 `electron/` 里的独立实现
- 一个子任务负责 `src/` 里的独立展示层适配
- 一个子任务负责验证或文档补齐

前提是：

- 它们不同时改共享数据结构
- 不同时改同一个主链路文件
- 不擅自改变接口 shape

#### 第四类：并发验证

在实现完成后，可以并发跑：

- `npm run lint`
- `npm run build`
- 改动文件静态诊断
- 只读 git 状态确认

但“是否完成”的结论仍然必须由主线统一给出。

### 14.18 你在实际使用 OMO 时，应该怎么做

如果你想让 OMO 真正做到可控并发，最实用的操作步骤不是“让它多开几个 agent”，而是按下面的顺序发指令。

#### 第一步：先让主线收敛，不要求并发实现

你应该先让 OMO 做这件事：

- 明确目标
- 明确不改什么
- 明确验收标准
- 明确第一版范围

这一阶段不要要求“同时开始做前后端和 UI”。

#### 第二步：让 OMO 先列共享契约

你应该要求它先明确：

- 核心数据结构是什么
- 接口 shape 是什么
- 哪些规则不能变
- 哪些文件属于共享契约

如果这些还没写清，就不要进入实现并发。

#### 第三步：让 OMO 拆工作流并标 ownership

你应该让 OMO 输出类似这样的内容：

- A 线：负责哪些模块
- B 线：负责哪些模块
- C 线：负责哪些模块
- 每条线允许改哪些文件
- 每条线禁止改哪些共享文件
- 每条线依赖哪些已冻结前提

只有 ownership 清楚，才有真正并发。

#### 第四步：只并发独立工作流，不并发共享契约

你实际推动时，应该允许并发的是：

- 独立模块实现
- 文档沉淀
- 验证准备
- 只读分析

你不应该允许并发的是：

- 同时改 `types`、`preload`、`global.d.ts` 这类共享契约文件
- 同时改一个主链路热点文件
- 一边改返回结构，一边让 UI 按旧结构继续写

#### 第五步：要求 OMO 主线统一集成

并发任务做完以后，不要直接让它说“完成了”。

你要让主线再做：

1. 集成
2. 验证
3. 文档更新
4. checkpoint / commit

这一步不能分散给多个工作流各自收口。

### 14.19 一个最实用的日常操作模板

如果你以后要在 OMO 里实际推动并发开发，可以直接按这个顺序来：

1. 先让 OMO 收敛目标、边界、验收标准。
2. 让 OMO 列共享契约和共享文件。
3. 让 OMO 把任务拆成 A/B/C/D 线，并标明 ownership。
4. 只批准那些“不改共享契约”的工作流并发推进。
5. 要求主线统一集成、统一验证、统一记录、统一提交。

这才是结合 OMO 当前系统形态后，真正可落地的并发工作方式。

### 14.20 `git commit` 和 `worktree` 在这套流程里是否必要

这两个机制都和“并发开发”有关，但必要性并不一样。

#### 14.20.1 `git commit`：通常是必要的

在当前 OMO 工作方式下，`git commit` 更像“保存节点”机制，而不是可有可无的习惯。

它的作用是：

- 固定一个稳定闭环
- 让后续工作可以从已验证状态继续
- 减少长会话里改动越堆越多、难以回退的问题
- 让文档记录、验证结果、代码状态形成对应关系

所以对于下面这些情况，`git commit` 基本都应该做：

- 一个稳定小闭环已经完成
- 已经通过 `lint`、`build` 或关键手动 QA
- 已经补好了任务记录或文档
- 即将进入下一轮不同主题的大改动

对当前 OMO 来说，`git commit` 比 `worktree` 更基础、更常用，也更必要。

#### 14.20.2 `worktree`：不是默认必要，是条件性机制

`worktree` 的作用不是“让项目更专业”，而是给真正独立的并行工作流提供物理隔离。

它主要解决的问题是：

- 两条工作线需要同时推进
- 但它们不能共享同一个工作目录
- 每条线都需要独立改动、独立验证、独立切换分支

在当前 OMO 模式下，`worktree` 不是默认必要，因为：

- 当前 OMO 的主模式是“主代理统一收敛 + 子代理并行产出”
- 很多并发其实停留在 discovery、文档、验证，而不是长期多线编码
- 如果没有真正独立的长期工作流，直接上 `worktree` 只会增加维护负担

所以：

- `git commit` 是默认应该有的保存机制
- `worktree` 是满足条件时才启用的隔离机制

### 14.21 什么情况下应该用 `worktree`

只有在下面这些条件同时接近成立时，`worktree` 才真正有价值：

1. 确实有两条或以上需要持续并发推进的编码工作流。
2. 这些工作流都不是只读分析，而是真的要长期改代码。
3. 它们有各自独立的分支、验证过程、提交节奏。
4. 它们的共享契约已经冻结，互相不会频繁改写前提。
5. 把它们放在同一个工作目录里会明显增加冲突或切换成本。

如果只是下面这些情况，就通常不值得上 `worktree`：

- 一个小 bug 修复
- 一次文档补充
- 一轮短 discovery
- 一个主线功能开发，只是中间有几个并发搜索任务
- 共享契约还没定下来

### 14.22 本项目里哪些场景值得考虑 `worktree`

以当前项目举例，下面这种情况可以考虑：

- A 线：继续做 `team/account` 身份识别和导入/刷新主流程
- B 线：独立重做大块 UI 结构或图表交互
- 两条线都要持续多天推进
- 两条线都要改很多文件
- 两条线最好各自独立构建、验证、提交

这时如果仍然共用一个工作目录，很容易出现：

- 频繁切分支
- 临时改动互相污染
- 一个方向的半成品影响另一个方向验证

这类场景下，`worktree` 是合理的。

反过来，像这次的 hover marker bug：

- 只涉及小范围修复
- 主要在 `src/App.tsx` / `src/styles.css`
- 验证链很短
- 改动量很小

这种情况就完全没必要上 `worktree`。

### 14.23 结合 OMO，使用 `worktree` 时技术上要注意什么

如果真的要用 `worktree`，技术上要注意：

- 每个 `worktree` 对应一条明确分支，不要多个工作流混在一个分支里
- 共享契约文件仍然要由主线统一管理，不要在多个 `worktree` 里各自改一版
- 每个 `worktree` 都要有自己的验证动作，不要以为主工作目录的验证结果能替代它
- 文档记录要写清楚：哪条工作流在哪个分支/目录推进、当前做到什么状态
- 最终合回主线前，仍然要统一集成验证，不能把“各自都能 build”当成“整体已完成”

### 14.24 落到实际，你该怎么判断用不用 `worktree`

你可以直接按这 5 个问题判断：

1. 现在是不是只有一条主编码线？
2. 当前并发是不是主要还是 discovery / 文档 / 验证？
3. 共享契约是不是还没冻结？
4. 这些工作是不是很快就能在一个闭环里做完？
5. 共用一个工作目录会不会真的造成明显冲突？

如果前四题大多回答“是”，第五题回答“不会”，那就不要用 `worktree`。

如果是下面这种答案组合：

- 不止一条长期编码线
- 不是只读并发，而是独立实现并发
- 共享契约已冻结
- 各自需要独立验证和提交
- 共用工作目录会明显互相干扰

那就应该考虑 `worktree`。

### 14.25 一套最实用的日常用法

对当前 OMO，最推荐的默认顺序是：

1. 先不用 `worktree`，先收敛目标、边界、验收标准。
2. 用主线推进 discovery、冻结共享契约。
3. 每完成一个稳定闭环就 `git commit`。
4. 只有当出现真正独立的长期编码工作流时，再引入 `worktree`。
5. 引入 `worktree` 后，仍然由主线统一做集成、验证、记录和最终提交策略。

一句话：

> `git commit` 是默认保存机制，`worktree` 是在真正需要物理隔离的长期并行编码时才启用的高级机制。

17. 再做第三条闭环：切换 active 账号。

## 16. 结论

全新项目从零开始时，最高效也最稳的方式不是“尽快写出很多代码”，而是：

- 先把问题定义清楚
- 再把第一版范围压缩清楚
- 再让工程具备最小运行能力
- 再定义数据、流程、模块
- 再按闭环逐条推进
- 每一轮都验证、记录、提交

一句话总结：

> 先串行定方向与共享契约，再并行推进独立工作流，最后串行集成、并行验证、串行收口。
