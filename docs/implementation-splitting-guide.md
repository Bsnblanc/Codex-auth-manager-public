# 实现阶段任务拆分规则说明（适配 OMO 工作方式）

## 记录目的

这份文档回答三个问题：

1. 进入实现阶段后，任务应该如何拆分。
2. 拆分规则应该如何制定，才不会拆错。
3. 这套拆分方式是否适配当前 OMO 的真实工作方式。

这份文档不是讲“两个完全不同需求如何并发”，那部分已经由 `docs/parallel-development-boundary-guide.md` 说明。

这份文档讲的是：

- 一个已经明确边界的大任务
- 进入实施阶段以后
- 应该怎样拆成可执行、可并发、可集成的实现工作流

## 1. 先定义这里说的“拆分”是什么

这里的拆分，不是：

- 随便把一个大任务切成几个文件名
- 把所有改动平均分给几个 agent
- 不考虑依赖关系，强行同时写代码

这里说的拆分，是指：

- 先明确共享契约
- 再识别哪些部分必须由主线统一掌控
- 再把剩余的大头实现拆成独立工作流
- 每条工作流都拥有自己的文件域、输入、输出、依赖和验收结果

一句话：

> 拆分的目的不是把工作切碎，而是把可以独立推进的实现真正隔离出来。

## 2. 为什么实现阶段必须拆分

一旦进入实施阶段，真正耗时的大头通常是编码，而不是解释需求。

如果不拆分，就会出现：

- 所有改动都堆在主线
- 一个热点文件承载所有变化
- 任何一处小变动都会阻塞全局
- 主线既要想规则，又要写实现，又要做验证

这会导致：

- 编码吞吐低
- 回归风险高
- 长会话越来越难控制

所以，实现阶段不是“能不能拆”，而是：

- 只要任务足够大，通常就应该拆。

## 3. 拆分前必须先完成什么

在真正拆实现之前，以下内容必须先明确。

### 3.1 目标和边界

必须明确：

- 改什么
- 不改什么
- 验收标准是什么

如果边界不清，就不能安全拆分，因为不同子任务会按不同理解各自推进。

### 3.2 共享契约

共享契约是所有实现线共同依赖的前提。

最常见包括：

- 数据结构
- 接口 shape
- 规则边界
- 验收标准

在当前项目里，典型共享契约文件包括：

- `electron/types.ts`
- `electron/preload.cts`
- `src/global.d.ts`
- `docs/subscription-identity.md`
- `docs/obtainable-fields.md`

### 3.3 主线热点文件

某些文件天然是主线热点，不适合多个工作流同时碰。

当前项目的典型热点包括：

- `src/App.tsx`
- `src/styles.css`
- `electron/main.cts`

拆分时必须先标出来，不能等子任务撞上去才发现。

## 4. 拆分规则如何制定

### 4.1 第一条规则：先拆共享契约，再拆实现

先判断：

- 哪些文件属于共享契约
- 哪些文件属于主线热点
- 哪些文件属于独立实现域

顺序不能反过来。

因为如果先拆实现，再回头改共享契约，前面拆出来的所有实现都有返工风险。

### 4.2 第二条规则：按依赖方向拆，不按文件平均拆

正确做法是按依赖链拆：

- 数据层
- 主流程层
- 展示层
- 文档/验证层

而不是：

- 你改 3 个文件，我改 3 个文件

文件数量平均，不代表依赖独立。

### 4.3 第三条规则：每条实现线只能有一个明确目标

每条工作流都必须回答清楚：

- 它的目标是什么
- 它的输入是什么
- 它的输出是什么
- 它依赖什么前提
- 它改哪些文件
- 它不能改哪些文件

如果一条线同时承担两个方向，就说明拆分还不够清楚。

### 4.4 第四条规则：共享热点文件默认只给主线

对于像下面这种文件：

- `src/App.tsx`
- `electron/main.cts`

默认应该由主线负责集成或最终落点。

子任务如果要碰，必须满足：

- 改动区域边界非常清晰
- 不会改变共享契约
- 主线已经明确批准该文件域可以拆出去

否则默认不要拆给多个子任务。

### 4.5 第五条规则：拆分结果必须能独立验证

一条子实现线如果做完后根本无法局部验证，那通常说明拆分还不成熟。

至少应该能做到下面之一：

- 局部静态检查
- 构建无新增错误
- 文档输出完整
- 结果能被主线集成后快速确认

### 4.6 第六条规则：每轮实现都要有明确记录者

实现阶段不仅要拆代码线，也要拆记录责任。

必须明确：

- 谁负责把用户本轮提问和回复留痕
- 谁负责把范围变化写进正确文档
- 谁负责记录本轮方案、输出、验证结果和未解决项

如果没有单独指定，默认规则是：

- 主线就是记录者

记录者不能只记“最后改了什么”，还必须记：

- 用户一开始要什么
- 中途是否修正了目标或解释
- 本轮明确不做什么
- 最终到底交付了什么

一句话：

> 没有记录者的实现线，不算真正收口的实现线。

## 5. 实现阶段最推荐的拆分方式

对当前 OMO 和当前项目类型，最推荐的是按下面四类工作流拆。

### 5.1 A 线：核心业务 / 主流程实现

负责：

- 主进程业务逻辑
- 数据流和状态落盘
- 关键业务规则真正执行

当前项目对应：

- `electron/main.cts`
- `electron/store.ts`
- `electron/jwt.ts`
- `electron/quotas.ts`
- `electron/opencode.ts`

### 5.2 B 线：UI / 展示实现

负责：

- 页面结构
- 展示层适配
- 样式与交互表现

当前项目对应：

- `src/App.tsx`
- `src/styles.css`
- `src/main.tsx`

### 5.3 C 线：规则 / 文档沉淀

负责：

- 产品规则
- 字段说明
- 任务记录
- 开发规则和流程文档
- 用户提问 / 回复的留痕整理
- 方案、结果、验证证据的归档

当前项目对应：

- `docs/product-spec.md`
- `docs/obtainable-fields.md`
- `docs/subscription-identity.md`
- 任务记录文档

### 5.4 D 线：工程 / 验证 / 基线维护

负责：

- 构建命令
- lint 和类型检查
- AGENTS 结构
- checkpoint / git 基线

当前项目对应：

- `package.json`
- `vite.config.ts`
- `AGENTS.md`
- 验证动作和 git 节点

## 6. 这套拆分是否适配 OMO 工作方式

### 6.1 结论

适配，但要按 OMO 的真实执行模型去用。

### 6.2 当前 OMO 的真实模型

当前 OMO 更接近：

- 主代理统一控需求边界
- 主代理统一冻结共享契约
- 子代理并行产出独立结果
- 主代理统一集成、验证、记录、提交

这意味着：

- 它适合“可控拆分”
- 不适合“多个 agent 长期同时改共享热点文件”

### 6.3 为什么适配

因为这套拆分方法正好符合 OMO 的优势：

- 主线适合管方向、管契约、管收口
- 子任务适合并行做边界清晰的独立实现
- 文档和验证也适合并发产出

### 6.4 为什么不能乱拆

如果你把共享契约也拆给多个子任务，就会违背 OMO 的真实工作方式，导致：

- 子任务理解不一致
- 主线集成成本暴涨
- 改动互相覆盖
- 验证结果失真

所以这套拆分适配 OMO，但前提是：

- 共享契约只给主线
- 独立实现才拆出去

## 7. 一套可直接执行的拆分制定步骤

下面这套步骤，是你在实际用 OMO 推项目时最实用的做法。

### 第一步：先让主线写出任务边界

主线必须先写出：

- 目标
- 不改什么
- 验收标准

没有这一步，不要进入拆分。

### 第二步：列共享契约清单

让主线先列出：

- 哪些数据结构是共享的
- 哪些接口 shape 是共享的
- 哪些规则边界不能由子任务改
- 哪些文件属于共享契约文件

这一步完成后，才能真正开始拆实现线。

### 第三步：标热点文件和可拆文件域

让主线明确两张表：

- 热点文件表
- 可拆文件域表

例如当前项目里：

- 热点文件：`src/App.tsx`、`electron/main.cts`
- 可拆文件域：`docs/`、部分 `electron/*.ts` helper、部分 `src/` 展示层适配

### 第四步：为每条工作流写 ownership

每条工作流都要写清：

- 名称
- 目标
- 输入
- 输出
- 可改文件
- 禁改文件
- 依赖前提
- 记录者是谁
- 这条线的记录要落到哪个文档

没有 ownership，就不叫真正拆分。

### 第五步：只把独立实现拆给子任务

此时才允许并发推进：

- 独立模块实现
- 文档沉淀
- 验证准备
- 规则整理

不要拆出去的包括：

- 共享契约修改
- 共享热点文件整合
- 最终集成逻辑

### 第六步：主线统一集成和验证

子任务产出后，仍然必须由主线做：

1. 合并思路
2. 集成代码
3. 跑验证
4. 更新文档
5. commit / checkpoint

这里的“更新文档”不是可选收尾，而是必须把本轮用户需求、用户修正、实施方案、结果和验证一起落档。

这一步不能再分散给各线各自收口。

## 8. 本项目里的具体示例

假设当前项目下一步要做“增强 team/account 身份识别与展示”。

正确拆分方式不是：

- 一个 agent 改一半 `src/App.tsx`
- 一个 agent 改另一半 `src/App.tsx`
- 再让另一个 agent 顺手改 `types`

正确做法是：

### 主线先冻结共享契约

- `electron/types.ts`
- `electron/preload.cts`
- `src/global.d.ts`
- `docs/subscription-identity.md`
- `docs/obtainable-fields.md`

### 然后拆实现线

- A 线：`electron/jwt.ts`、`electron/quotas.ts`、`electron/main.cts` 中独立可拆部分
- B 线：`src/App.tsx` 的展示适配、`src/styles.css` 的样式适配
- C 线：规则文档和任务记录
- D 线：验证路径、构建确认、checkpoint 准备

### 最后主线收口

- 主线统一检查是否都遵守了共享契约
- 主线统一做 lint/build/QA
- 主线统一补记录和提交

## 9. 一句话判断拆分是否合理

判断一套拆分是否合理，只问三句话：

1. 共享契约是不是已经先冻结了？
2. 每条线是不是只改自己的文件域？
3. 最后是不是仍由主线统一集成和验证？

如果三句都能回答“是”，这套拆分通常就合理。

如果其中任何一句回答“不是”，说明这不是正确拆分，而只是把复杂度分散了。

## 10. 结论

实现阶段的任务拆分，不是为了“让更多 agent 同时写代码”本身。

它真正的目标是：

- 先把必须统一的部分收敛
- 再把真正独立的大头编码拆出来并行推进
- 最后由主线统一集成、验证和提交

一句话总结：

> 拆分规则的核心，不是平均分工，而是先定共享契约，再按独立文件域和独立目标拆实现线；这套方式适配 OMO，但必须由主线统一控契约、控集成、控收口。
